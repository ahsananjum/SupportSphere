# Privacy request operations

This is an operator procedure for the current SupportSphere foundation. It is not a promise of a particular legal response period or an automatic retention schedule. The operator must review applicable law and any preservation obligation before release or deletion.

1. Receive access, correction, or deletion requests at `ahsananjum170@gmail.com`. Record the request and response in a restricted operator log; do not put personal information or credentials in source control or application logs.
2. Confirm the requester controls the relevant email address. For workspace data, also confirm their account and the workspace involved. A sender's claim alone is insufficient. If an account owns a workspace, arrange ownership transfer or workspace closure before deleting the account.
3. In Supabase Dashboard for project `xviumgygixcklrbuynoh`, inspect **Authentication → Users** and **Database → Tables** for `profiles`, `workspace_members`, `workspace_invitations`, `workspaces`, `audit_logs`, and `contact_submissions`. Search by the normalized email and then by the confirmed user ID and workspace ID. Check Brevo transactional events if the request concerns email delivery. The `contact_rate_limits` table contains keyed hashes rather than plaintext email/IP and is cleaned after expiry by the contact intake service.
4. For access/export, extract only records belonging to that verified person. Workspace records may contain other members' information; review and redact those fields before sharing. Send the export through a private channel to the verified address. Never paste a production export into chat or a repository issue.
5. For correction, change only the confirmed person's fields after verifying the source of truth. For deletion, review ownership and foreign-key dependencies first. Remove eligible contact submissions and invitations in the Supabase SQL Editor, using a reviewed transaction scoped to confirmed IDs. Remove workspace membership through the role-aware product flow where possible. Supabase Auth user deletion follows only after ownership and invitation references are resolved. Audit records may need to remain for security or legal reasons; document the reason and restrict access rather than silently deleting them.
6. Re-query the affected tables and Auth user record to verify the requested change. Record which categories were changed, any records retained with a reason, and the date of response in the restricted operator log. Reply to the verified requester without including unrelated workspace data.

Only the operator or an authorized administrator should use dashboard/SQL access. The public contact endpoint cannot export or delete records, and its service credential must never be exposed to the browser.
